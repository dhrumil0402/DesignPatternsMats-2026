# Phase 2 — Factory Method (Requirements)

This is the **assignment**. Implement from these requirements. If you get stuck or want to check your design, use the [guided check](guided-check.md) (signatures and partial snippets — not a complete solution).

After you implement, answer the [questions](./questions.md).

## Purpose

Introduce the **Factory Method** pattern for creating heterogeneous **sensor** devices (moisture vs light) with type-specific defaults, persist them in PostgreSQL, and show them in the dashboard **Sensors** section.

When you finish this phase, Phase 3 can extend the same `devices` table with actuators and `device_family` without redoing sensor creation.

## Scope and naming rules

- Persist sensors in a single `devices` table (not a `sensors` table). Use a `role` of `sensor` so Phase 3 can add actuators in the same table.
- Callers (HTTP handlers, UI) must not construct moisture/light sensors with scattered constructors. They go through a creator interface.
- Domain types stay free of FastAPI, SQLAlchemy, and Pydantic.
- ORM models live in infrastructure. Alembic migrations are **autogenerated** from those models — do not hand-write the `devices` table script.

## Outcome required at end of phase

- `docker compose up` starts **PostgreSQL, backend, and frontend** (dev containers); Scalar and the dashboard are reachable on localhost without separate host uvicorn/npm terminals.
- `devices` table exists with columns needed for sensor identity, type, role, display name, default config, and created timestamp.
- Factory Method creators produce moisture and light sensors with distinct default configurations.
- `POST /api/sensors` creates a persisted sensor; `GET /api/sensors` lists them after a backend restart.
- Dashboard Sensors section lists sensors and can add moisture and light types.
- Scalar documents the sensors endpoints.
- Pattern note exists at `docs/patterns/factory-method.md`.

## Required architecture for this phase

- **Domain layer**
  - Sensor entity (plain Python).
  - Abstract creator with `create_sensor`; concrete moisture and light creators.
  - Lookup that maps a type key (for example `moisture` / `light`) to a creator.
  - Must not depend on FastAPI, SQLAlchemy, or Pydantic.

- **Application layer**
  - Service that asks a creator for a prototype, then persists via a repository.
  - Optional request/response DTOs (inline Pydantic on the router is acceptable in this phase if mapping stays out of domain).

- **Infrastructure layer**
  - Declarative SQLAlchemy `Base` and `DeviceRow`.
  - Repository that saves and lists sensor rows, mapping to/from the domain entity.
  - Session dependency for FastAPI.
  - Alembic `target_metadata` wired to `Base.metadata` so autogenerate sees the model.

- **API layer**
  - `GET` and `POST` under `/api/sensors`.
  - Unknown type → 400. Successful create → 201.
  - Router stays thin: parse input → service → map to response.

- **Frontend**
  - Typed API helpers for list/create.
  - Sensor list UI mounted in `#sensors` with add actions, loading/error/empty states.

- **Dev Compose (this phase)**
  - Extend Phase 1 `docker-compose.yml` with `backend` and `frontend` services (bind mounts + reload).
  - Backend talks to Postgres via hostname `postgres` inside the Compose network.
  - Browser still uses `http://localhost:8000` and `http://localhost:5173` (published ports).

## Type hints

Domain `Sensor` (plain Python, not an ORM row):

| Field | Hint |
|-------|------|
| `id` | `UUID \| None` (None before persist) |
| `device_type` | `str` (e.g. `moisture_sensor`, `light_sensor`) |
| `display_name` | `str` |
| `default_config` | `dict` |

ORM `devices` (`DeviceRow`):

| Column | SQL / mapping hint |
|--------|-------------------|
| `id` | UUID PK, server default `gen_random_uuid()` |
| `device_type` | `String(64)`, not null |
| `role` | `String(32)`, default `"sensor"` |
| `display_name` | `String(128)`, nullable |
| `default_config` | JSONB, default `{}` |
| `created_at` | timestamptz, server default `now()` |

API JSON:

| Direction | Shape |
|-----------|--------|
| POST body | `{ "type": string, "display_name": string \| null }` — `type` is the creator key (`moisture` / `light`), not `device_type` |
| Response | `{ id: UUID, device_type: str, display_name: str, default_config: object }` |

Frontend `SensorDto`: `id: string`, `device_type: string`, `display_name: string`, `default_config: Record<string, unknown>`.

## Step-by-step implementation requirements

## Step 1 — Full-stack Compose (backend + frontend)

Phase 1 left Compose as **Postgres only** and ran the API/UI on the host. In this phase, add **dev containers** so one Compose command runs the stack. Host venv/`npm run dev` may remain for debugging; Compose is the **required** path for acceptance checks from here on.

Implement:

- `backend/Dockerfile` — Python 3.11+, install the project (including Alembic), run Uvicorn with `--reload` on `0.0.0.0:8000`.
- `frontend/Dockerfile` — Node 20, install deps, run Vite with `--host 0.0.0.0` on port 5173.
- Extend root `docker-compose.yml` with `backend` and `frontend` services:
  - Bind-mount source so hot reload works inside the containers.
  - Publish ports `8000` and `5173`.
  - Backend `DATABASE_URL` must use hostname **`postgres`** (Compose service name), not `localhost`.
  - `depends_on` Postgres with a health condition; frontend may depend on backend.
  - CORS / `VITE_API_BASE_URL` stay browser-facing (`http://localhost:8000`) because the browser runs on the host.

Acceptance criteria:

- `docker compose up --build -d` (or equivalent) shows postgres, backend, and frontend running.
- `GET http://localhost:8000/health` reports `"db": "ok"`.
- Dashboard loads at `http://localhost:5173/dashboard`.
- Alembic from this phase onward can be run with `docker compose exec backend alembic ...` (working directory as needed).

## Step 2 — Persistence models (before migration)

Define infrastructure ORM **before** generating a migration.

Required `devices` columns:

| Column | Purpose |
|--------|---------|
| Identifier | UUID primary key |
| `device_type` | e.g. `moisture_sensor`, `light_sensor` |
| `role` | `sensor` in this phase |
| `display_name` | Optional human label |
| `default_config` | JSON defaults from the creator |
| `created_at` | Timestamp |

Index `role` (useful for Phase 3 filters).

Wire Alembic so autogenerate compares `Base.metadata` to the database. Import the models module from `env.py`; otherwise autogenerate produces an empty upgrade.

Add a database session generator the API can depend on.

Acceptance criteria:

- ORM lives in infrastructure, not domain.
- `alembic revision --autogenerate` would see the `devices` table (you generate it in Step 3).

## Step 3 — Generate migration via Alembic

Do **not** hand-write the table.

- Preconditions: full Compose stack up (Step 1), Phase 1 revision current, models and `target_metadata` saved.
- Generate a revision with a message such as `devices` (prefer `docker compose exec backend alembic revision --autogenerate -m "devices"`).
- Review `upgrade()`: `create_table("devices", ...)` with the expected columns; `down_revision` is the Phase 1 id.
- If `upgrade()` is empty, fix metadata wiring, delete the bad file, regenerate.
- Apply with `docker compose exec backend alembic upgrade head` (or equivalent). Never edit an already-applied revision.

Acceptance criteria:

- `alembic current` (via Compose exec) is the new revision.
- Database inspection shows `devices` with the expected columns.
- Migration chain is forward-only.

## Step 4 — Domain: entity + Factory Method

Implement:

- A sensor entity with id (nullable before persist), device type, display name, and default config.
- An abstract creator with `create_sensor`.
- At least two concrete creators (moisture, light) with **different** default configs (units, sampling interval, moisture threshold, and similar).
- A registry/lookup so the application layer selects a creator by a short type key, not by importing concrete classes in the router.

Acceptance criteria:

- HTTP handlers do not instantiate sensor types directly.
- Unknown type keys fail in domain/application before a useless insert.

## Step 5 — Repository and application service

Repository:

- Save a sensor as a `devices` row with `role="sensor"`.
- List sensors (filter by role), newest first.
- Map rows back to domain entities (including generated id).

Service:

- Resolve creator → `create_sensor` → `save`.
- List delegates to the repository.

Acceptance criteria:

- Create path always goes through a creator.
- List after restart still returns rows (commit actually happens).

## Step 6 — REST API

Expose:

- `GET /api/sensors` — list.
- `POST /api/sensors` — body includes type key and optional display name.

HTTP behavior:

- 201 on create with id, device_type, display_name, default_config.
- 400 on unknown type with a useful detail message.
- Register the router on the FastAPI app; tag routes so Scalar groups them.

Acceptance criteria:

- Empty list is `[]` before any creates.
- Moisture vs light POSTs return distinct `default_config`.
- Scalar **sensors** tag shows GET and POST.
- Restart backend; GET still returns created rows.

## Step 7 — Frontend Sensors section

- Extend the API client with sensor types and list/create functions. JSON field names must match the backend.
- Replace the Sensors placeholder with a list that can add moisture and light sensors.
- Show loading, error, and empty states.
- After refresh, the list still shows persisted sensors.
- Keep other dashboard placeholders for later phases.
- Use Tailwind conventions from Phase 1.

Acceptance criteria:

- User can add both sensor types from the UI.
- Refresh still shows them.

## Step 8 — Tests

Minimum:

- Unit tests: moisture creator defaults include a moisture-related key; light creator uses a different unit/type.
- Optional integration test for GET/POST against a test client.

Acceptance criteria:

- Creator tests pass without a database.

## Common pitfalls to avoid

- Leaving backend `DATABASE_URL` pointed at `localhost` inside Compose (use hostname `postgres`).
- Hand-writing the migration instead of autogenerate.
- Forgetting to import models in Alembic `env.py` (empty upgrade).
- Putting SQLAlchemy models in the domain package.
- Instantiating `MoistureSensor` in the router instead of going through a creator.
- Not committing the session (empty list after create).
- Skipping Scalar registration (`include_router`).
