# Phase 3 — Abstract Factory (Requirements)

This is the **assignment**. Implement from these requirements. If you get stuck or want to check your design, use the [guided check](guided-check.md) (signatures and partial snippets — not a complete solution).

After you implement, answer the [questions](./questions.md).

## Purpose

Introduce the **Abstract Factory** pattern to provision **coherent device families** (simulation vs edge): each factory creates a matching set of **sensors and actuators** with family-specific defaults. Persist `device_family` on the existing `devices` table and expose a unified devices API plus dashboard UI.

Factory Method (Phase 2) still creates individual sensor *types*. Abstract Factory **orchestrates** those creators plus actuator prototypes into one bundle per family.

## Scope and naming rules

- Reuse the `devices` table. Add `device_family`; do not create a second devices table.
- Families in this phase: at least **`simulation`** and **`edge`**.
- Each provisioned kit includes sensors **and** actuators (same table, different `role`).
- Domain `Device` is not an API DTO. HTTP uses a separate DTO + mapper.
- Abstract Factory and repository use domain `Device` only — they must not import Pydantic DTOs.
- Migrations are autogenerated from ORM changes; do not edit applied revisions.

## Outcome required at end of phase

- `devices.device_family` exists; existing rows are backfilled (default simulation).
- Provisioning a family persists a coherent kit (sensors + actuators) with that family’s key and distinct defaults.
- `GET /api/devices` can filter by family and role.
- Dashboard can switch family, provision a kit, and list devices with role/family badges.
- Scalar documents device endpoints and the device DTO schema.
- Pattern note exists at `docs/patterns/abstract-factory.md`.

## Required architecture for this phase

- **Domain layer**
  - Unified `Device` entity (id, type, role, family, display name, config).
  - Abstract family factory with a family key and `create_device_set()`.
  - Concrete factories for simulation and edge.
  - Lookup by family key.
  - Sensor Factory Method creators remain; family factories compose them.
  - No FastAPI / SQLAlchemy / Pydantic.

- **Application layer**
  - Device DTO and mapper (domain → DTO). Mapping does not live on the domain entity.
  - Family service: resolve factory → create set → persist → return domain devices (or DTOs only at the boundary).

- **Infrastructure layer**
  - `device_family` column (and useful index) on `DeviceRow`.
  - Repository methods to save one/many devices and list with optional family/role filters.
  - Sensor save path sets a family (default simulation) so old rows stay consistent.

- **API layer**
  - List and provision under `/api/devices`.
  - Returns DTO schemas. Unknown family → 400.
  - Thin router.

- **Frontend**
  - TypeScript `DeviceDto` matching JSON keys.
  - Family switcher + device list + provision action.

## Step-by-step implementation requirements

## Step 1 — Extend the ORM model

Add `device_family` on `devices`:

- Non-null string.
- Server default such as `simulation` so existing sensor rows remain valid.
- Index on `device_family` for filtered lists.

Acceptance criteria:

- Model change is in infrastructure only.
- No new table for “families”.

## Step 2 — Generate and apply migration

Autogenerate with a message such as `device_family`.

Review:

- `add_column` for `device_family`.
- Index creation if modeled.
- If Alembic emits nullable-then-NOT-NULL without backfill, add an `UPDATE` for existing rows before tightening nullability — or rely on a server default that backfills.

Apply to local database. Confirm with table inspection.

Acceptance criteria:

- `alembic current` is the new revision.
- `\d devices` shows `device_family`.
- Existing Phase 2 sensors still load.

## Step 3 — Unified domain `Device`

Introduce a frozen (or otherwise immutable) `Device` covering both sensors and actuators.

You may keep Phase 2 `Sensor` and map at the repository, or treat `Sensor` as a thin alias. Minimum: listing sensors still works.

Acceptance criteria:

- Domain device includes `role` and `device_family`.
- Domain does not import DTOs.

## Step 4 — Abstract Factory implementations

Implement an abstract factory that returns a **list of devices** belonging together.

Required families:

| Family | Intent |
|--------|--------|
| `simulation` | Dev/sim kit: matching labels and `protocol`/config for simulation |
| `edge` | Distinct labels and config (stub hardware); not a copy of simulation strings |

Each `create_device_set()` should include **two sensors and two actuators** (for example moisture, light, water pump, grow light). Sensors should still be produced via Phase 2 creators, then tagged with the family.

Unknown family keys raise a domain/application error.

Acceptance criteria:

- Simulation and edge kits differ in `device_family` and in at least some config (for example protocol).
- Factory Method creators are composed, not deleted.

## Step 5 — Repository, service, DTOs

Repository: save device (all roles), save a list, list with optional `device_family` and `role` filters. Map rows to `Device`.

Service: `provision_family(family)` and `list_devices(...)`.

DTOs:

- Read model with id, device_type, role, device_family, display_name, default_config.
- Mapper function(s) in application layer. Do not put `from_domain` on the DTO if that pulls mapping into the wrong place; keep mappers dedicated.
- Factory and repository never import the DTO.

Acceptance criteria:

- Provision persists every device in the set.
- Filters actually constrain SQL/list results.
- Scalar schema for the DTO matches JSON.

## Step 6 — REST API

- `GET /api/devices` with optional query params `family` and `role`.
- `POST /api/devices/provision` with required family (query or body — pick one and document it). Returns 201 and the created DTO list.
- Unknown family → 400.
- Register router; tag `devices`.

Keep `/api/sensors` working. Optional: refactor sensor responses to the same DTO style — not required.

Acceptance criteria:

- Provision simulation → 4 devices; provision edge → 4 devices with edge family.
- Filter by family returns only that family.
- Scalar **devices** tag documents both operations and `DeviceDto`.

## Step 7 — Frontend

- API client: list (with filters) and provision. TypeScript fields match backend JSON.
- Family switcher (simulation / edge).
- Device list with role and family badges; empty and error states.
- Provision button for the selected family; reload after success.
- Mount in a **Devices** dashboard section (keep Sensors for Factory Method). Tailwind conventions from earlier phases.

Acceptance criteria:

- Switching family reloads the filtered list.
- Refresh still shows provisioned kits from PostgreSQL.

## Step 8 — Tests

Minimum:

- Simulation factory: four devices, one family key, both roles present.
- Edge factory differs from simulation (family and at least one config value).
- Optional API integration: provision 201 length 4; GET filter includes actuators.

Acceptance criteria:

- Factory tests pass without requiring HTTP.

## Step 9 — Documentation

Create `docs/patterns/abstract-factory.md`:

- Problem (matching sensors + actuators per environment).
- Solution (family factory + concrete families).
- Contrast with Factory Method (one product vs product line).
- Where in code; why `Device` ≠ DTO.
- Extension exercise (a third family).

## Common pitfalls to avoid

- Deleting Factory Method creators instead of composing them.
- Returning domain entities directly from the router (no DTO).
- Letting the factory import Pydantic.
- Empty autogenerate because `env.py` does not import models.
- Existing sensors missing family because migration skipped backfill/default.
- UI showing mixed families because the list request omitted the filter.
